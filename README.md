# Digital Modus Operandi — сайт агентства

Продакшен: https://digital-modus-operandi.vercel.app

Одностраничный сайт с разделом кейсов. Vite + React + wouter + TypeScript, SPA без
SSR; серверной части нет, кроме serverless-функции заявок (`api/lead.ts`). Пакетный
менеджер — **только pnpm**: в репозитории `pnpm-lock.yaml` и патч зависимости
в `patches/`, npm/yarn сломают установку.

## Быстрый старт

```bash
pnpm install
pnpm dev        # http://localhost:3000
```

## Команды

| Команда        | Что делает                                                                |
| -------------- | ------------------------------------------------------------------------- |
| `pnpm dev`     | dev-сервер с HMR на порту 3000 (`--host`, доступен по сети)               |
| `pnpm build`   | продакшен-сборка в `dist/public` + генерация `sitemap.xml` и `robots.txt` |
| `pnpm preview` | локальный просмотр собранного `dist/public` (порт 4173)                   |
| `pnpm check`   | проверка типов: исходники и, отдельным проходом, тесты                    |
| `pnpm test`    | `vitest run` — тесты контента, клиентских утилит и функции заявок         |
| `pnpm format`  | Prettier по всему репозиторию (`--write`, меняет файлы)                   |

Тесты серверной функции лежат в `tests/`, а **не** рядом с ней в `api/`: всё,
что попадает в `api/`, Vercel считает serverless-функцией — компилирует своим
tsconfig и публикует как эндпоинт. `.vercelignore` отсекает тестовые файлы от
сборки на всякий случай.

`pnpm check` намеренно делает два прохода. Основной `tsconfig.json` исключает
`**/*.test.ts` (иначе тестовые типы текли бы в сборку), поэтому тесты
проверяются отдельно по `tsconfig.test.json` — без этого ошибки типов в тестах
всплывали бы только на деплое. Перед коммитом: `pnpm check`, `pnpm test`,
`pnpm build`.

## Архитектура

Точка входа — `client/src/main.tsx` → `client/src/App.tsx`, где на wouter объявлены
три маршрута: `/` (`client/src/pages/Home.tsx`), `/cases`
(`client/src/pages/Cases.tsx`) и `/cases/:slug` (`client/src/pages/CaseDetail.tsx`);
всё остальное отдаёт `NotFound`. Главная собрана из секций в
`client/src/components/site/` (`Hero`, `Problems`, `Services`, `CasesSection`,
`Process`, `Trust`, `Team`, `Faq`, `Contact`, общая обёртка `SiteShell`) — каждая
секция только раскладывает вёрстку, текст в неё приходит из `client/src/content/`.
Вспомогательное: `client/src/lib/seo.ts` (title/description/OG/JSON-LD проставляются
на клиенте), `client/src/lib/leads.ts` (отправка формы), `client/src/lib/analytics.ts`.

Стили — один файл `client/src/index.css`: CSS-переменные (палитра, типографика,
motion) плюс классы секций; Tailwind подключён, но основная вёрстка держится на
собственных классах. Токены и правила их применения описаны в
`design/design-system.md` — правки палитры и типографики сверяйте с ним.

## Контент: где что лежит

Весь текст сайта вынесен из JSX в `client/src/content/`. Правка текста — это правка
одного из этих файлов, лезть в компоненты не нужно.

| Файл          | Что внутри                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `types.ts`    | типы всех сущностей контента; менять — только вместе с компонентами                                                                   |
| `site.ts`     | `brand` (название, email, telegram, город), `primaryCta`, `navItems` (меню), `hero`, `marqueeWords`, `problems`, `finalCta`, `footer` |
| `services.ts` | блок «Что разрабатываем»                                                                                                              |
| `process.ts`  | блок «Как работаем»: шаги и что требуется от клиента                                                                                  |
| `trust.ts`    | блок про подход/доверие                                                                                                               |
| `team.ts`     | участники команды                                                                                                                     |
| `faq.ts`      | вопросы и ответы                                                                                                                      |
| `cases.ts`    | кейсы + производные списки (`featuredCases`, `publishedCases`, `draftCases`)                                                          |

**Контакты** (email, телеграм, город) — только в `brand` в `site.ts`; компоненты
и mailto-фолбэк формы берут их оттуда. **Пункты меню** — массив `navItems` там же;
`href` — это якорь на `id` секции главной (`#services`, `#cases`, …), новый пункт
без соответствующей секции просто никуда не проскроллит.

### Как добавить кейс

Правило, которое надо понять до того, как открывать `cases.ts`: заказчик запретил
публиковать выдуманные цифры. Поэтому у каждого кейса есть поле `proof` — один
факт, который можно подтвердить (статус использования, финансирование, награда,
реальная цифра от клиента), и поле `status`:

- `status: "published"` — факты подтверждены. Кейс получает страницу
  `/cases/<slug>`, попадает в список `/cases`, может выводиться на главной и
  добавляется в `sitemap.xml` при сборке.
- `status: "draft"` — подтверждённых фактов пока нет. Кейс показывается на `/cases`
  в блоке «Другие проекты команды» одной строкой, но собственной страницы не имеет
  (`CaseDetail` отдаёт 404) и в `sitemap.xml` не попадает.

Если фактов от клиента ещё нет — кейс остаётся `draft`. Не надо «пока» ставить
`published` с придуманным `proof`: это ровно то, от чего уходили.

Порядок действий:

1. Добавьте объект в массив `cases` в `client/src/content/cases.ts`. Обязательны все
   поля из типа `CaseStudy` (`client/src/content/types.ts`): `slug`, `client`,
   `industry`, `title`, `subtitle`, `problem`, `solution`, `functions`, `result`,
   `proof`, `tags`, `cover`, `nda`, `team`, `status`, `featured`. `ndaNote` —
   только при `nda: true`.
2. `slug` — латиницей, он же URL: `/cases/<slug>`. Должен быть уникальным.
3. `cover` — один из четырёх вариантов оформления обложки:
   `"case-lime" | "case-violet" | "case-ice" | "case-peach"` (классы в `index.css`).
4. `featured: true` — вывод на главной. Туда попадают только `published` и не
   больше четырёх (`featuredCases` в конце `cases.ts` режет список).
5. Под NDA: подробности архитектуры и бизнес-процессов не пишем в `functions`
   и `solution`, а честно помечаем `nda: true` + `ndaNote`.
6. `pnpm check && pnpm build`, затем проверьте, что слаг появился в
   `dist/public/sitemap.xml`.

Образец — существующий кейс из `cases.ts`:

```ts
{

  client: "Tehnosklad",
  industry: "Бытовая техника / Комрат",
  title: "E-commerce-платформа, которой заказчик управляет без разработчика",
  subtitle:
    "Публичный каталог, гибкие характеристики и админ-панель, рассчитанная на сотрудника компании.",
  problem:
```

### Как добавить участника команды

Участники — массив `team` в `client/src/content/team.ts`. Поля: `id` (`D-0x`, выводится
на карточке), `name`, `role` (2–3 функции, капсом), `bio` (одно предложение),
`skills`, `portrait` (`portrait-a` … `portrait-d` — стиль плейсхолдера) и
необязательные `image` + `imageAlt`.

Фотография кладётся файлом в `client/public/team/` и подключается путём от корня
сайта: `image: "/team/nikita.jpg"`. Требования к файлу и список ожидаемых
портретов — в `client/public/team/README.md`. Пока файла нет, карточка сама
показывает плейсхолдер-досье (`onError` в `client/src/components/site/Team.tsx`),
битой картинки посетитель не увидит.

## Деплой и переменные окружения

Vercel собирает проект из ветки `main` автоматически: пуш в `main` → продакшен,
пуш в любую другую ветку / PR → preview-деплой. Команда сборки и выходная
директория заданы в `vercel.json` (`pnpm build` → `dist/public`), там же rewrite
всех не-`/api` путей на `/index.html` и заголовки кеширования.

Форма заявки отправляет POST на `/api/lead` — это serverless-функция `api/lead.ts`
(валидация, антиспам, доставка). Ей нужны две переменные, задаются в
**Vercel → Project → Settings → Environment Variables** для окружений Production
и Preview:

- `TELEGRAM_BOT_TOKEN` — токен бота от @BotFather;
- `TELEGRAM_CHAT_ID` — чат, группа или **несколько получателей через запятую**:
  `670030360,-1001234567890`. Заявка уходит каждому независимо; пробелы вокруг
  запятых и повторы отбрасываются. Отказ одного получателя не отменяет отправку
  остальным: заявка считается доставленной, если её принял хотя бы один чат,
  а отвалившийся пишется в лог отдельной строкой.

Работают только в паре. Если канал не настроен, функция отвечает 503, а форма
предлагает скопировать текст и отправить его боту или написать напрямую —
поля при этом не очищаются, заявка не теряется молча.

**Самопроверка канала.** Откройте `/api/lead?check=1` в браузере: функция
скажет, видит ли она свои переменные, принимает ли Telegram токен и пускает ли
бота в каждый из чатов. Проверка только читает (`getMe` и `getChat`), никому
ничего не отправляет и не выдаёт наружу ни токен, ни номера чатов — чаты
нумеруются в том порядке, в каком перечислены в переменной. Обычный `GET`
без `?check` по-прежнему отвечает 405.

Типовая причина, по которой заявки не доходят при верных переменных: получатель
**не нажимал `/start`** в боте. Telegram не даёт боту написать первым и отвечает
`chat not found` — самопроверка покажет это отдельной строкой.

**Токен — секрет.** В репозиторий не кладётся (`.env` в `.gitignore`) и **не должен
получать префикс `VITE_`**: переменные с этим префиксом Vite вшивает в публичный
бандл, то есть токен утечёт всем посетителям. `VITE_` допустим только для
неcекретных значений вроде `VITE_SITE_URL`. Список переменных с комментариями —
в `.env.example` (шаблон, значения туда не вписываются).

Локально `/api/lead` не поднимается: `pnpm dev` запускает только Vite, без
serverless-функций. Проверять доставку заявок — на preview-деплое.

## Грабли

- **Фотографии команды.** До переработки портреты грузились по пути
  `/manus-storage/...`, который обслуживает только dev-сервер. В продакшен-сборку
  такие файлы не попадают, и на Vercel карточки были пустыми. Сейчас файлы лежат
  в `client/public/team/` и попадают в сборку как обычная статика. Не возвращайте
  ссылки на dev-only пути.
- **Шаблонный мусор вычищен — не тащите его обратно.** Проект вырос из шаблона
  генератора: полсотни неиспользуемых shadcn-компонентов, express-сервер со
  сломанным скриптом `start`, OAuth-хелпер генератора. Всё удалено вместе с
  49 зависимостями. Дизайн-система проекта — это `client/src/index.css` и
  `design/design-system.md`, а не shadcn. Если понадобится готовый компонент,
  `components.json` на месте и `shadcn add` доставит нужный поштучно.
- **SPA без SSR.** Прямой заход на `/cases/tehnosklad` работает только благодаря
  rewrite в `vercel.json`. Меняете правило — проверяйте, что внутренние URL не
  начинают отдавать 404. Мета-теги проставляются на клиенте (`lib/seo.ts`);
  для шаринга главной в `client/index.html` есть статические title/description/OG,
  для отдельных кейсов статический HTML с верными мета-тегами генерируется
  при сборке (`scripts/prerender-seo.ts`).
- **Sitemap генерируется из контента** при `pnpm build`, а не руками. Забыли
  пересобрать — новый кейс не появится в `dist/public/sitemap.xml`.
